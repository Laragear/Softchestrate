# ASD-STE100 rules for code comments

This page applies the core rules of ASD-STE100 (Simplified Technical English) to doc comments and inline comments. It is a working subset, not the full specification. The approved dictionary is not reproduced here: when a word has a plain, common alternative, use the plain one and keep it fixed for the whole project.

## Sentences

- **Maximum 20 words per sentence.** Split longer sentences. Count words in the summary sentence too.
- **One instruction or fact per sentence.** A sentence with a condition and a result is fine: "Returns `null` when the key is missing."
- **Active voice.** Name the actor. Prefer "The method stores the value." over "The value is stored."
- **Present simple for descriptions.** "Returns", "stores", "throws". Use "will" only for a future event.
- **No ambiguous pronouns.** Repeat the noun instead of "it", "this" or "that" when the referent is not obvious.
- **No idioms, no slang, no humor.** Write what the code does and nothing else.

## Words

- **One word, one meaning.** Pick one term for each concept and keep it: "key" or "name", not both for the same thing. Do not alternate "item", "element" and "entry" for one thing.
- **No synonyms for control.** Use "use", not "utilize". Use "start", not "initiate". Use "end", not "terminate", unless the code's own term is "terminate".
- **Modal verbs have one meaning each:**
  - "can" for ability or possibility: "The method can return `null`."
  - "may" for permission: "You may pass `null` to disable the limit."
  - "must" for a requirement: "The key must not be empty."
  - "should" for a recommendation: "You should call `flush()` before shutdown."
  - "will" for future: "The next call will reset the counter."
- **Avoid "-ing" forms as noun modifiers.** Write "the cache key", or "the key for the cache", not "the caching key". "Returns the parsed value." is fine: it is a participle describing the result.
- **Avoid these words in descriptions:** "etc.", "and so on", "as well as", "various", "some", "several", "basically", "simply", "just".
- **Units and numbers.** Use numerals and state the unit: "5 seconds", "1024 bytes". Write "0" or "1" as numerals in code terms.

## Paragraphs

- **One topic per paragraph.** Doc comment summaries and behavior notes are separate paragraphs.
- **Keep paragraphs to 1 to 3 sentences.**
- **Put the condition before the result** when a sentence has both, or split it into two sentences.

## Examples

| Avoid | Write |
| --- | --- |
| Utilizes the caching mechanism to retrieve the entry if it exists, otherwise it is generated. | Returns the cached value. Generates and caches the value when the key is missing. |
| This method is basically a wrapper around the parsing logic for various formats. | Parses the input string. Supports JSON and YAML. |
| The caching key is passed. | The cache key is passed. |
| Will throw if the key is invalid or possibly empty. | Throws `InvalidArgumentException` when the key is empty. |
| The limit can be set to nothing, etc. | You may pass `null` to disable the limit. |
| The job gets retried when it has been failed for some reason. | The job retries when it fails. |

## Checklist

Before you finish a comment:
- Each sentence has 20 words or fewer.
- Each sentence states one fact or one instruction.
- Each concept has one term, the same term everywhere in the file.
- Each modal verb has its meaning from the list above.
- No pronoun points to an unclear noun.
- Each claim matches a line of code you read.
